# The Maze RPG — State of the Project & Implementation Plan

**Last updated:** 2026-07-24
**North star:** the "dream state" is [Game Idea.md](../Game%20Idea.md), with supporting numbers/systems from [Levels and Stats.xlsx](../Levels%20and%20Stats.xlsx) and the class/race evolution material in [Game Class and Stats.drawio.xml](../Game%20Class%20and%20Stats.drawio.xml). **As of 2026-07-24, the long-term vision expands beyond the dungeon** — see "Dungeon-as-Trial + Overworld" below, which is now the guiding frame for everything past Phase 1.
**Accepted for now:** fully automatic (real-time) movement and combat stays the *default* feel. A player-toggleable turn-based mode is planned as an additive precision tool (see below), not a wholesale control-model conversion. Manual/turn-based-always is not the direction.

## 0a. North-star pivot (2026-07-24): Dungeon-as-Trial + Overworld

The owner's long-term goal, discussed with reference to Cataclysm: Dark Days Ahead and Dwarf Fortress (Adventure mode), and independently corroborated by an architecture proposal drafted with ChatGPT: give the player genuine open-ended freedom — mine ore, become a merchant with a stall, become a mage-scholar inventing spells, tear down a house and rebuild it — via a **small set of universal systems whose interactions create freedom**, rather than scripting each lifestyle individually. Roles (miner, merchant, scholar) should emerge from capability (tools, skill, knowledge, standing) rather than being locked classes.

**Decision: TheMazeRPG stays the base**, not the SimpleRPG prior attempt (see the Prior-Attempt Reference section below for the comparison that led here). Reasoning, briefly: `GameState` is already headless/UI-decoupled (every `TEST_*` demo proves this), we already have a working `Combinable`/`CombinationEngine` merge system, a stable-id content-registry seed (`classes.json`/`races.json`/`Attack.Id`), and a typed/tooled language — all of which SimpleRPG lacks and would need to be rebuilt from zero regardless of which codebase "wins." The one real point in SimpleRPG's favor (it's already turn-based + player-input-driven) is being addressed differently: see the turn-based toggle below, which is additive rather than a full conversion.

### The structural idea: Dungeon = Trial, Overworld = the persistent sandbox

- **Origin story**: the player character is a newly-sentient being who comes into existence *inside* the dungeon — no family, no prior world-knowledge, full autonomy and sentience from the start. This diegetically explains the blank-slate start and justifies the dungeon as a bounded, separate space rather than a gameplay-convenience hand-wave.
- **The Dungeon** is close to what already exists — procedural maze floors, the auto-play combat loop, `EnemyFactory`-generated enemies, loot, XP, the Codex. Analogous to a **Trial** in J.T. Wright's *The Infinite World* web serial (the same series referenced in `Ideas/infinite_world_system_reference_manual.html` found during the SimpleRPG review) — a bounded high-risk/high-reward space you enter and return from, rather than the entire game.
- **Safe room + Guardian gate, every 4 floors — IMPLEMENTED 2026-07-24** (see progress log below for the full build). Corrected model vs. the first draft of this section: the safe room is an **interstitial space** between floor groups (e.g. "floor 4.5"), not a floor that replaces floor 5 — floors 1-4 are normal, then a safe room, then floors 5-8 resume normally, then another safe room, etc. Regular floors no longer have their own embedded boss at all (removed) — the only boss-tier fight is the gate **Guardian**, met by choice in the safe room. A bespoke small room with a shrine glowing faint blue (mana-colored) in the center, and a door on the far side leading to that gate's Guardian. Touch the shrine to return to the Overworld (currently a placeholder hook, since the Overworld doesn't exist yet); push through the far door to challenge the Guardian. Restful effect while inside (boosted HP/Stamina/Mana/Faith regen). Deeper gates' Guardians scale up naturally (same level-scaling formula as the old per-floor boss, fed a higher `CurrentFloor`). Leaving is never gated behind beating a Guardian.
- **The Overworld** is new: a persistent, open, capability-driven sandbox in the Cataclysm/DF spirit. This is where the "endless choices" vision actually lives — mining, crafting, building/dismantling structures, running a merchant stall, magical research — and where ChatGPT's proposed architecture (Simulation / World / Actors / Actions / Activities / Content registry / thin UI / Persistence, with Cataclysm-style data-driven `copy-from` inheritance and a start/do_turn/finish/cancel/resume Activities model) is the target internal shape. The spell-as-grammar idea (Effect + Element + Delivery + Shape + Duration + Modifiers + Cost) for *inventing new base spells* is complementary to, not competing with, our existing `CombinationEngine` (which handles *recombining existing* spells/items/abilities) — both are likely wanted eventually.
- **Pause vs. turn-based toggle (finalized 2026-07-24)**: two distinct, additive features. (1) A plain **pause**, available at any time, anywhere — freezes the tick driver, no stepping. (2) A **turn-based mode**, intended mainly for complex/difficult moments (a hard fight, a delicate crafting/building action) — the tick driver pauses and advances deliberately on player input instead of the timer. Real-time auto-play stays the default everywhere; neither feature is a control-model conversion.
- **First-region scope (finalized 2026-07-24)**: see [Starting Region.md](../Starting%20Region.md) for the full spec — a single procedurally-generated-once-then-fixed town anchored at the dungeon entrance, small enough to build and verify end-to-end before expanding.

**Still open**: whether the dungeon (beyond the first exit opportunity) is a true one-time prologue or an ongoing loop the player can return to later — deferred; not load-bearing for the first slice, since the first slice only needs one clean entry→exit pass to prove the Dungeon→Overworld handoff.

**2026-07-24 — Real save/load persistence IMPLEMENTED and verified.** Closes the "only survives within one running process" gap flagged right above. - **Polymorphic serialization**: `Combinable` now carries `[JsonPolymorphic]`/`[JsonDerivedType]` attributes (`Weapon`/`Spell`/`Ability`/`Item`, discriminated by a `$kind` field) so `List<Combinable>` (Loadout/Inventory) round-trips through JSON without losing which concrete type — and therefore which fields (`BaseDamage`, `ManaCost`, `Modifiers`, ...) — each entry actually is.

**2026-07-25 — Player controls as a mode (the agency layer, first cut).** The long-flagged "no player-input system" gap, done the way the owner framed it: *modes*, never removing auto-run. `GameState.ControlMode` (`Auto` default / `Manual`), toggled live.

- **Manual** hands movement to the player: `Tick()`'s movement block branches to `MovementSystem.MoveHeroByDirection` (free directional movement, vector-normalized so diagonals aren't faster, per-axis round-to-cell walkability so the hero wall-slides), driven by a `_manualMoveX/Y` intent the UI sets from held keys. Held-key set → intent vector, recomputed on every down/up. Pausing clears held keys + zeroes intent so the hero doesn't drift on un-pause. **2026-08-06 — Tile/door/room model IMPLEMENTED and verified (PR 2).** `TileType` (`Wall/Floor/DoorClosed/DoorOpen/DoorLocked`) is now the single terrain authority; `Maze.Walls` became a read-only derived view (`BlockingGrid`) so all 33 existing call sites — collision, LOS, projectiles, both renderers — kept working untouched. The proxy is deliberately read-only: C# rejected assigning through it, which was the right answer, since writing `false` would silently flatten a door into floor. The 7 terrain-write sites now name the tile they mean. `TileType.Wall` is 0 where `bool[,]` defaulted to *open*, so the constructor fills `Floor` explicitly rather than letting the default silently invert.
- **The load-bearing distinction: walkable ≠ traversable.** The first attempt at generating doors took the suite from 26/26 to **1/26** — closed doors read as blocked, so every room fell off the pathfinding graph (stairs unplaceable, connectivity assertions failing). `IsWalkable` (can I stand here now) governs collision; `IsTraversable` (can I get through by opening it) governs pathing and connectivity. Locked doors are excluded from both, which is precisely what will make a vault a vault. `BfsDistancesFrom`, the tactical/enemy path searches, and the generation validator all moved to the traversable graph.
- **Behaviour**: shut doors block movement *and sight*, so a room keeps its contents hidden until opened; bump-to-open for hero and enemies (shouldering a door costs a tick); locked doors need a key (`TryUnlockDoor`).

Corridors now route **door-to-door**: each room gets a single threshold punched through its wall ring on the side facing its neighbour (`ChoosePort`, boundary-safe, refusing ports that touch two rooms — rooms may sit one tile apart), and the corridor joins the two outside tiles. ## 2. Design decisions that must be made before building

These are genuine forks where the two north-star docs disagree or under-specify. Pick deliberately; each unblocks a chunk of the plan.

1. **Stat model: 10-point allocation vs. 28-by-class.**
   `Game Idea.md` §Stats says "start at 1, distribute 10 points." The xlsx says "28 base stats, distribution by class" (and the code implements this faithfully).
   *Recommendation:* keep the 28-by-class base (already built and matches the sheet) **and** layer an optional small allocation pool on top during character creation for the Game Idea.md flavor. Reconciles both.

2. **Race modifiers: additive vs. multiplicative.**
   Code applies flat integer bonuses (`Data/Races/races.json`, e.g. Elf Agility +2). The xlsx explicitly specifies **multipliers, rounded** — with a worked example: "a 4 in strength for a human means 4, but for a dwarf means 5.2 → 5." The multipliers are already tabulated in the sheet (Human 1.0, Dwarf Str/Con 1.3, Elf Int 1.25 / Agi 1.2, Goblin Cha 0.4, …).
   *Recommendation:* switch to the multiplicative model — it's a small, well-specified data+formula change and makes races actually matter.

3. **Race roster mismatch.**
   Code races: Human/Elf/Dwarf/Halfling/**Orc/Tiefling/Dragonborn**. xlsx races: Human/Elf/Dwarf/Halfling/**Goblin/Kobold**. Decide the canonical roster (the drawio has lore for Goblins specifically, incl. a reputation/HERO-tag mechanic).

4. **XP curve.**
   Code is exponential (`ExperienceToNext *= 1.5`, `Core/Models/Hero.cs:98`). The xlsx tabulates quadratic candidates (100·L² → 100/400/900/1600…) out to level 65, plus two alternatives.
   *Recommendation:* adopt the quadratic curve from the sheet; it's a one-line change and makes the authored XP tables meaningful.

5. **Attack identity.**
   Attacks are currently matched by **substring on their display name** for both visuals and special behavior (e.g. arrow art only renders for names containing "Bow"/"Arrow" — so Archer's "Quick Shot" silently loses its art; "Arcane Blast" radius growth is independently string-matched in two files). This must move to stable IDs/tags before attacks become data-driven (see §4). Decide the ID scheme now.

## 4. The keystone: a unified "Combinable" model

Everything that makes the dream *this game* — items, spells, abilities, and the merge system that ties them together — depends on one architectural decision. `Game Idea.md` says spells combine with spells/items/abilities, items with items/spells/abilities, abilities with abilities/spells. That is impossible to build cleanly if items/spells/abilities are separate hardcoded types. Build a common substrate **first**.

**Proposed shape (Phase 1–2):**
- `Combinable` (base/interface): `Id`, `Name`, `Kind` (Weapon / Item / Spell / Ability / Armor), `Rarity` (Common→Mythic), `Attributes` (a set of tags: Fire, Ice, Lightning, Shadow, Holy, Poison, Arcane, Sharp, Heavy, Light, Fragile, Cursed, Blessed…), `Level`, and effect payload (damage, scaling stat, cooldown, resource cost, on-hit effects).
- `CombinationEngine`: `Combine(a, b, contextLocation) → Combinable`, applying the rules from `Game Idea.md`:
  - same attribute → **intensify** (Fireball + Fireball → Fireball+),
  - different attributes → **new blended attribute** (Fire + Ice → Frostfire; Fire + Shadow → Infernal special-case),
  - cross-kind → **new kind** (Bow + Fireball → Fire Bow *item*; Fireball + Dense Musculature → Fire Fist *ability*),
  - **rarity math** (point-value model from the doc: common+rare → uncommon),
  - **level math** (result at lower of the two; a rarity increase resets to level 0),
  - **location gating** (spells anytime; weapons only at anvil/forge; abilities only at a shrine).
- **`Attack` becomes a runtime projection** of an equipped Weapon/Spell/Ability rather than a hand-authored `AttackFactory` switch. This is also what retires the fragile name-substring matching (§2.5): projections carry stable IDs/tags that drive both combat behavior and rendering.
- `DiscoveryRegistry` / **Codex** — records every base and combined entity the player has discovered, with descriptions; persists across runs (the "library of items and spells" unlockable).

Get this right and items, spells, abilities, merging, and the codex all fall out of one system. Get it wrong (separate silos) and every later phase fights the architecture.

## 5. Phased roadmap to the dream state

Dependency-ordered. Each phase is shippable and playable. Sizes are rough: S (hours), M (days), L (1–2 wks), XL (multi-wk).

### Phase 0 — Foundation fixes & cleanup  *(see §3)*  — **S–M total**
Clock, combat wind-up, dead code, debug gating, settings wired. Nothing new; everything after this is built on a trustworthy base.

### Phase 1 — Data-model foundation  — **L**
*Goal: the nouns of an RPG exist as data, and xlsx numbers are honored.*
- Introduce `Combinable` base + `Item`, `Spell`, `Ability` deriving from it (§4). Don't build combining yet — just model + equip + use.
- Refactor `AttackFactory`'s hardcoded switch into **data-driven attacks projected from equipped Weapon/Spell** (stable IDs/tags; kills the substring matching, fixes Archer art as a side effect).
- Basic **inventory + equip** (a few hotbar-style slots per `Game Idea.md`'s "key item slots").
- Align to xlsx: **quadratic XP curve** (decision 2.4), **multiplicative race modifiers** (decision 2.2), **monster tiers** (Basic/Elite/Boss with the sheet's XP rewards) replacing `10 + MaxHp/4`.
- **Codex data structure** (discovery list) even if the UI is minimal.
- *Touchpoints:* new `Core/Models/Item.cs`, `Spell.cs`, `Ability.cs`, `Combinable.cs`; rewrite `Core/Services/AttackFactory.cs`; `CharacterDataService` race math; `Hero` leveling; `GameState` enemy spawn + XP.

### Phase 2 — The merge / combine system  — **L–XL**  *(the signature feature)*
*Goal: the mechanic the whole design is built around.*
- `CombinationEngine` with the full rule set (§4): same/different attribute, cross-kind, rarity math, level math.
- **Combine locations** in the maze: reuse the dormant `MazeFeatureType.Shrine` (abilities) and add anvil/forge (weapons); spells combine anytime.
- Result discovery → Codex; combined entities **persist** (they're usable in future runs per the doc).
- A **combine UI** (even simple: pick two, preview result, confirm/swap/inventory per the "swap, combine, or send to inventory" flow).
- Seed the recipe space with the doc's worked examples (Frostfire, Fire Bow, Bubble Bow, Fire Fist, Fire Affinity, Holy Flame, Rapier, Sniper…) as validation cases.
- *Depends on:* Phase 1 model. *Unblocks:* most of the "unlockables" fantasy.

### Phase 3 — Character builder & progression depth  — **M–L**
*Goal: the pre-run builder and in-run growth match the doc.*
- Character creation: **stat-point allocation** (decision 2.1), **ability selection** (max by species), **save slots / templates** ("save character as template, adjust in future games").
- **Save system** (JSON under a user profile dir): templates, unlocked races/classes/abilities, Codex, run history. Cross-cutting; introduced here, extended later.
- **Spells/abilities level with use**; player levels with kills (per doc); spell evolution choices on level-up.
- *Touchpoints:* `Views/CharacterSelectWindow.*` (major expansion), new `Core/Services/SaveService.cs`, `Hero`/`Spell`/`Ability` leveling.

### Phase 4 — Run structure, meta & unlockables  — **L**
*Goal: a roguelite loop with persistence and reasons to replay.*
- **Boss-gated portal progression**: boss defeat unlocks the stairs/portal (wire up the currently-write-only `Boss` property). Chest→key can remain a secondary gate or become loot.
- **End-of-run stats screen** (kills, damage dealt/taken, floors, loot score) — replaces the bare death overlay; both north-star docs call for it.
- **Unlock system**: races (Human→Manaborn line), classes, abilities unlocked through play; **class & species evolution** — see [Class Tree Inventory.md](../Class%20Tree%20Inventory.md) (authoritative, 2026-07-24): 6 starter Commons → 11 action-unlocked Common specializations (e.g. "punch an enemy to death" → Monk, "kill an enemy with a sword" → Spellsword) → level-gated Uncommon/Rare/Epic/Legendary evolutions at 10/25/50/75 → Mythical. Families branch and share nodes across starter classes (Duelist bridges Rogue/Warrior, Paladin bridges Warrior/Priest, Monk bridges Priest/Wanderer); Mage Apprentice's Elementalist line further splits into 6 elemental sub-trees. Implementation-wise this is a big content/data-authoring lift once Phase 1's `Combinable`/class model stabilizes — plan to model it as data (per-class unlock rules + evolution tables), not hardcoded branches in C#.
- **Endless mode** after the final floor.
- *Depends on:* save system (Phase 3), items/abilities (Phase 1–2).

### Phase 5 — World & NPCs  — **XL**
*Goal: the living-world layer.*
- **NPCs / towns / merchants / trainers**, scaling down in frequency by floor (per doc).
- **Followers** (Charisma-gated) and follower buffs.
- **Environment / chunk effects** (fire weak in rain, water weak in volcano).
- **Village-defense mode** (the xlsx/drawio "monsters mass at a portal and march on a village; keep a population % alive").
- Reputation / alignment (Goblin HERO-tag mechanic; evil vs. good branches feeding Phase 4 evolutions).
- Largest and least-specified; revisit scope when Phases 1–4 land.
